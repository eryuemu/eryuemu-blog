# 一次宽带欠费造成的乌龙

> **症状**：昨夜挂机跑高并发 Docker 爬虫，中午回来发现电脑无法上网。`ping 223.5.5.5` 100% 丢包，访问外网 HTTPS 报 TLS EOF，但 `curl -6` 访问 B 站正常，DNS 也能解析出公网 IP。同时局域网内另一台跑 QQ Bot 的 Fedora 机器也暴毙，容器内 TCP 全断。  
> **初诊**：结合挂机爬虫、新建连接失败、老连接存活、IPv6 正常等现象，Trae AI 给出自信诊断——**“高并发任务打爆了家用路由器的 NAT 连接跟踪表（conntrack）”**。  
> **转折**：拔电重启路由器后并未恢复，反而跳转至 `lock.he.cninfo.net`，舍友一句提醒瞬间揭开真相——**纯粹是宽带欠费停机**。  
> **延伸**：为什么欠费停机后还能通过 IPv6 和 Trae 顺畅对话？Clash Verge 的 TUN 模式下到底该不该开 IPv6？实测防漏真实 IP 与分流细节。

---

## 0. 结论与复盘速览

| 排查节点 | 表象 / 误导推断 | 真实的底层事实 |
|---|---|---|
| **起因现象** | 昨晚通宵跑 Docker 抓取任务，中午发现 IPv4 全瘫 | 纯属扣费周期的巧合，宽带恰好在凌晨/上午余额清零停机 |
| **连带暴雷** | Fedora 机器上的 QQ Bot 也挂了，容器 TCP 全断 | Bot 走 IPv4 连腾讯服务器，同样被运营商机房阻断 |
| **关键误导** | 舍友在打游戏，Trae 据此判定“老连接存活，新建连接被丢弃” | 舍友当时实际也卡了或手机悄悄切了流量，后来自查账单才知欠费 |
| **Trae 诊断** | 判定家用路由器 conntrack 表耗尽，给出“路由器挂了重启就好” | 典型的把教科书案例生搬硬套到偶发巧合上的“完美误诊” |
| **铁证推翻** | 重启路由器非但没好，反而重定向到 `lock.he.cninfo.net` | 运营商机房（BRAS）在 IPv4 做了欠费拦截劫持；交费后秒恢复 |

| **后续延伸** | 开启 TUN + IPv6 下实测是否有泄漏 IP 与偷跑流量隐患 | 节点自带 IPv6 出网，Fake-IP 接管严密无泄露；但常规使用仍建议关闭代理 IPv6 防断流 |

## 1. 起因：一个挂了一夜爬虫的平平无奇中午

昨晚睡觉前，我在本机 Ubuntu 上启动了一个 Docker 容器，跑新浪视频归档的备份抓取项目（`archiveteam/sinavideo-grab`），想着挂在后台慢慢跑。同时，电脑上日常开着 Clash Verge 的 TUN 模式接管系统网络。

今天中午 12:48 左右，我坐回电脑前准备干活，顺手开几个网页，发现浏览器一直在转圈。打开终端一测，情况非常诡异：

```bash
# 1. 尝试 ping 阿里云公共 DNS，全部超时
eryuemu@eryuemu-P16-Pro:~$ ping -c 4 223.5.5.5
PING 223.5.5.5 (223.5.5.5) 56(84) bytes of data.
--- 223.5.5.5 ping statistics ---
4 packets transmitted, 0 received, 100% packet loss, time 3077ms

# 2. curl 访问网站，报 TLS 异常中断
eryuemu@eryuemu-P16-Pro:~$ curl -v https://www.bilibili.com
* Host www.bilibili.com:443 was resolved.
* IPv6: fdfe:dcba:9876::12
* IPv4: 198.18.0.16
* Trying [fdfe:dcba:9876::12]:443...
* TLS connect error: error:0A000126:SSL routines::unexpected eof while reading
curl: (35) TLS connect error: error:0A000126:SSL routines::unexpected eof while reading

# 3. 单独测试 IPv4，直接卡死超时
eryuemu@eryuemu-P16-Pro:~$ curl -4 -I https://www.baidu.com
^C

# 4. 但是！测试 IPv6，秒返回 200 OK！
eryuemu@eryuemu-P16-Pro:~$ curl -6 -I https://www.bilibili.com
HTTP/2 200 
date: Tue, 08 Sep 2026 04:22:37 GMT
content-type: text/html; charset=utf-8
server-timing: total;dur=10

# 5. DNS 解析也是完全正常的
eryuemu@eryuemu-P16-Pro:~$ nslookup baidu.com
Server:		127.0.0.53
Address:	127.0.0.53#53

Non-authoritative answer:
Name:	baidu.com
Address: 111.63.65.103
Name:	baidu.com
Address: 124.237.177.164
```

总结一下当时的现场症状：
* **IPv4**：完全瘫痪，ICMP ping 100% 丢包，TCP 握手全部 timeout 或被重置。
* **IPv6**：生龙活虎，访问 B 站等国内大厂 CDN 极其丝滑。
* **DNS**：解析正常，能拿到正确的公网 A 记录。

## 2. 现场排查与多机连环“暴雷”

面对这种怪现状，我的第一反应是：**昨晚挂的爬虫把系统网络栈搞乱了，或者是代理软件的虚拟网卡卡死了。**

我立刻开始了一连串的盲目自救操作：
1. `sudo systemctl stop docker`：把抓取容器先干掉。
2. `sudo ip link set dev Meta down && sudo ip link delet Meta`：怀疑是 Clash Verge 的 `Meta` 虚拟网卡出 Bug，直接把网卡干碎。
3. `sudo systemctl restart NetworkManager && sudo systemctl restart systemd-resolved`：重启网络管理与 DNS 解析服务。

结果一测，毫无改观——IPv4 依然不通，IPv6 依然活蹦乱跳。

更要命的是，我放在旁边做服务器的另一台 **Fedora 电脑**也暴雷了：
那台机器上常驻跑着一个 QQ Bot（基于 Docker 的 NapCat），几乎在同一时间点掉线，日志里疯狂报错：“连接不上腾讯服务器，DNS 解析仅返回 IPv6，IPv4 有地址但容器无 IPv6，容器内 TCP 彻底中断”。

两台物理机在同一个局域网下，同时遭遇 IPv4 阵亡、IPv6 存活的状况，这让我意识到：**问题肯定不在我这台电脑的单个配置上。**

---

## 3. Trae 登场：教科书级别的“完美误判”

我把两台电脑的报错和自己执行的命令一股脑发给了 Trae。

Trae 刚开始怀疑是我手动执行 `ip link delet Meta` 触发了连锁反应，把系统的内核转发参数 `net.ipv4.ip_forward` 带成了 0。我马上纠正它：**Fedora 那台机器压根没装 Clash，纯净跑 Docker，它怎么也断了？**

Trae 沉思片刻，根据我提供的信息，展开了一场极其合情合理、逻辑极其严密的推理：

1. **前提一**：昨晚挂了高并发的视频归档抓取脚本，持续发起了数以万计的瞬时连接；
2. **前提二**：我随口提了一句“舍友在打游戏，暂时不方便折腾路由器”；
3. **前提三**：IPv4 的新建连接全死，但已有的连接（舍友的游戏）似乎还在跑；
4. **前提四**：IPv6 天然不需要经过 NAT 转换，所以丝毫不受影响。

Trae 得出结论：
> “破案了！这是非常典型的**家用路由器 NAT 连接跟踪表（conntrack）被长跑任务打爆**。路由器的内存被数以万计的失效连接占满，因此会强行丢弃所有新的 IPv4 SYN 包，而老连接和 IPv6 不受影响。解决方法很简单，把路由器拔电重启一下即可。”

为了让我能跟 Fedora 机器上的 AI 同步情况，Trae 甚至贴心地精简了一句 9 个字的口诀：“**路由器挂了重启就好**”。

此时的我对这个解释深信不疑：理论扎实、现象严丝合缝、甚至把舍友在玩游戏都解释得通，简直就是教科书级的网络运维现场！

---

## 4. 剧情急转：重启后的运营商“暴击”

因为舍友在打游戏，我只能一直耐心等待。期间 Trae 还很负责地帮我检查了本机环境，确认我之前敲的 `ip link delet Meta` 不会有任何残留，只要以后开 TUN 会自动重建。

终于等到舍友的一局游戏结束，我立刻冲到客厅，果断拔掉路由器电源，静置十秒，重新插上。

等路由器绿灯重新常亮，我满心欢喜地打开电脑连上 Wi-Fi，准备迎接恢复，结果屏幕右下角和手机顶部同时弹出了一个熟悉的提示弹框：

> **“此 Wi-Fi 需要登录/认证”**

我点击认证，浏览器跳转却卡在一半打不开。

这时舍友在屋里喊了一声：“哥们，咱这宽带……是不是没费了啊？”

我赶紧在终端看了一下重定向的目标 URL，赫然写着：  
`http://lock.he.cninfo.net/...`

打开手机查了一下这个域名——**河南联通宽带欠费/停机专属认证拦截页面**！

**破案了，彻彻底底地破案了！**
* 根本没有什么高并发打爆连接表；
* 根本没有什么 Docker 转发参数失效；
* 舍友当时可能游戏早卡掉了或者手机自动切了 5G 流量；
* **纯粹就是宽带在今天扣费后欠费停机了！**

随后舍友在联通 App 里充值补齐了网费。过了两分钟，没有任何多余操作，电脑上的 `ping 223.5.5.5` 瞬间 0% 丢包，百度和外网全部满血复活。

## 5. 灵魂拷问：欠费停机了，为什么还能跟 AI 聊几个小时？

在这个乌龙事件中，最让我百思不得其解的是：  
**既然宽带早就欠费了，我为什么能全程毫无卡顿地在 Trae 里跟它聊了几个小时的排查？**

Trae 随后的解释彻底戳中了国内运营商的技术盲区：

1. **运营商的欠费拦截只管 IPv4**：  
   国内很多省份的运营商（比如河南联通），其机房侧的宽带扣费与门禁控制网关（BRAS）依然是几十年前基于 IPv4 体系搭建的。一旦欠费，系统会将所有公网 IPv4 的 80/443 请求强行劫持并 302 重定向到 `lock.he.cninfo.net` 停机页（这也是我之前访问 HTTPS 报 TLS EOF 的根本原因——因为证书不匹配被强制切断）。
2. **IPv6 是漏网之鱼**：  
   由于历史架构原因，运营商的 IPv6 流量很多并没有接入这套古老的欠费拦截网关。只要光猫物理链路没断，IPv6 是直接透传到骨干网的。
3. **大厂服务全面双栈化**：  
   Trae 的 API 服务端、国内大厂的 CDN（包括 B 站、智谱等）全部支持原生 IPv6。当我的操作系统发现 IPv4 握手全部超时后，底层协议栈（Happy Eyeballs 算法）自动悄悄把所有出网请求降级切到了 IPv6。

于是在我完全断网、宽带停机的一下午里，我硬生生靠着联通的 IPv6 骨干网，白嫖着带宽跟 AI 探讨了几个小时的“路由器连接表原理”。

## 6. 延伸思考：Clash Verge 的 TUN + IPv6 该不该开？

网络完全恢复之后，我突然想起自己在 Windows 上用代理软件时，一直习惯性地把 **IPv6 开关关掉**（只留 IPv4）。而这次在 Linux 的 Clash Verge 上，由于默认配置，我一直开着 **TUN 模式 + IPv6**。

借着这个机会，我顺手在终端做了一整套底层路由和反射测试，看看**开启代理软件的 IPv6 + 虚拟网卡到底会不会导致真实 IP 泄露或者偷跑流量**。

### 实测结果

通过纯 TUN 虚拟网卡（不设置终端代理环境变量）发起无污染测试：

```bash
# 1. 境外纯 IPv6 测试（访问海外 IP 反射服务）
$ curl --noproxy "*" -s https://v6.ident.me
2a12:e100:21:0:114:514:1919:810

# 2. 境外 Cloudflare 链路追踪
$ curl --noproxy "*" -s https://cloudflare.com/cdn-cgi/trace | grep -E "ip|loc"
ip=103.151.173.210
loc=JP

# 3. 国内直连测试
$ curl --noproxy "*" -s http://myip.ipip.net
当前 IP：2408:821a:5310:f870:xxxx  来自于：中国 河北 保定  联通
```

测试表明：
* **防漏 IP 表现良好**：我当前的代理节点配置很良心，落地机自身自带 IPv6 出口（返回了那个很有梗的 `114:514:1919:810` 地址），访问外网时全部被 TUN 的 Fake-IP 捕获并扔进了代理隧道，对端完全看不到我真实的河北联通 IPv6；
* **国内分流正常**：访问国内服务命中 Direct 直连规则，正常走本地物理网卡直连，不会白白消耗机场流量。

### 经验与避坑建议

既然开着没问题，那为什么圈内普遍建议**关闭代理软件的 IPv6** 呢？
经过这次排查，我总结了以下几点：

1. **节点兼容性坑（断流/卡顿）**：  
   市面上 90% 以上的机场节点是没有 IPv6 落地能力的。如果你开着 IPv6，访问像 Google、ChatGPT、GitHub 这类双栈网站时，系统会优先尝试发起 IPv6 连接。如果节点不支持，客户端必须傻等几秒握手超时后才会回退到 IPv4。**平时感觉某些外网转圈几秒才加载出来，绝大多数是 IPv6 超时在作怪。**
2. **裸 IP 直连风险**：  
   在没有开启 `strict-route`（严格路由）的情况下，域名访问会被 Fake-IP 拦截，但如果有冷门程序直接往裸 IPv6 地址发包，流量是有可能绕过虚拟网卡直接从物理网卡溜走的。
3. **日常使用的最佳实践**：  
   * **没必要强求 IPv6**：除非你有特殊的教育网/校园网纯 IPv6 免流需求，或者玩 PT/BT 需要公网做种，否则对于看网页、写代码、查资料，**直接在 Clash Verge 设置里关闭 IPv6** 是最稳妥、最防漏、延迟最低的选择。

---

## 7. 写在最后

这起排查乌龙给我的最大启示是：**当一个技术问题看起来充满了各种复杂的底层证据、并与你刚刚做的高深操作巧合重叠时，先不要急着分析内核与协议栈——先去看看网线插没插好，欠费了没有。**

奥卡姆剃刀法则诚不欺我：“如无必要，勿增实体”。最简单的可能，往往才是真相。
